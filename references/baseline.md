# 基线口径与校准

阈值不是拍脑袋定的。做法：取孙某《我的女友甜》正文（6.5K 字、272 段的第一人称克制白描长文）当语料，用 `scripts/style_check.mjs` 自身的统计口径逐段测量，把结果写回脚本顶部的 `BASELINE` 常量。

进仓库的只有下面这张表的统计量。原文文本只有一处例外：README 开头那两行共 26 个字的标注引用，用来交代方法来源；除此之外本仓库不含原文任何一句——文风可以量，文本不能抄。

## 复算方法

任何一份纯文本稿都能测：

```bash
node scripts/style_check.mjs corpus.txt          # 人读报告
node scripts/style_check.mjs corpus.txt --json   # 机读指标
```

`--json` 输出里的 `stats` 就是上表全部字段。拿别的语料重测时，只要文本是"一段一句、以空行分段"，同一套口径可以直接对比。

## 校准纪律

1. `BASELINE` 必须和脚本自身的正则同口径。改了数字正则、`sayParas` 判定或分节符识别，就要重跑语料，把新值写回 `BASELINE`——否则"基线"和"实测"是两把尺子，报告全废。
2. 词表改动后要查误报：把语料喂回去，必须 0 红线、100 分。达不到就说明词表里混进了正常中文常用词。
3. 已知踩过的两个坑：`最后` 是正常时间词，不能进 AI 套话表；`我意识到`、`我明白了` 这类第一人称陈述在优秀语料里合法出现，只抓 `我终于明白`、`我忽然明白`、`让我意识到` 这种总结腔。
4. 阈值是描述，不是及格线。一篇 300 字的小红书文案不可能同时满足全部节奏项，脚本对短稿会自动跳过段长/句长检查，只保留数字密度和红线。

## 查重口径（可复跑）

仓库里每份文本文件与原文做中文 8 字滑窗比对：先把两侧都剥成纯汉字串（去标点、去英文数字），再取 8 字窗口求交集。剥成纯汉字是为了避免"改了标点就算原创"这种自欺。

```js
const cjk = (s) => (s.match(/[\u4e00-\u9fff]/g) || []).join("");
const grams = (s, n = 8) => { const m = new Set(); for (let i = 0; i + n <= s.length; i++) m.add(s.slice(i, i + n)); return m; };
// corpus 为原文纯文本；file 为待查文件
const A = grams(cjk(fs.readFileSync("corpus.txt", "utf8")));
for (const g of grams(cjk(fs.readFileSync(file, "utf8")))) if (A.has(g)) console.log(g);
```

当前结果：README 命中 5 处，全部落在开头两行引用里（"三点五微克"与"五千万美元现金"在原文中前后相邻，剥掉标点后接缝连成窗口）；其余十份文件命中 0 处。

## 用真实 PDF 全文交叉验证

把孙某那篇《我的女友甜》的 PDF 全文（剥掉页码、按空行分段）喂给同一脚本，得到的指标与上面基线逐一吻合：

| 指标 | 真实 PDF 实测 | 仓库基线 | 结论 |
| :--- | :--- | :--- | :--- |
| 数字密度 | 2.59 个/百字 | 2.45 | 吻合 |
| 对话独立成段 | 31.3% | 30.1% | 吻合 |
| 问号 | 0.77 个/千字 | 0.77 | 吻合 |
| 分节符 | 0.77 个/千字 | 0.77 | 吻合 |
| 感叹号 / 省略号 | 0 / 0 | 0 / 0 | 吻合 |
| 句长中位 | 14 字 | 13 字 | 吻合 |
| 段长中位数 | 419 字（失真） | 15 字 | 排版失真 |

段长中位数在 PDF 提取里会失真：PDF 按页排版，多段被并成一块，脚本测出 419 字。所以段长一项仍以网页原版的 15 字为准，不用 PDF 提取值。其余项证明这把尺子确实是从原作量出来的，不是另写的。

窗口取 8 是刻意收紧的：中文常用 4 字成语很容易在任意两份文本里撞车，取 6 以下全是噪声，取 10 以上则等于只查整句照抄。
